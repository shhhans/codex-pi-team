## Objective recap

Close GitHub Issue #6: the three active roles must publish meaningful,
verifiable Blackboard updates at every observable lifecycle node (slice
start, key progress, blocked, completion, waiting), and long-running
slices must keep doing so without degrading into high-frequency
heartbeats. The Blackboard remains observation-only — no task control,
acceptance, or peer-transport authority is granted.

## Design observations from the ready_for_acceptance cycle

Two structural facts were demonstrated by the runtime itself during the
hand-off, not by tests:

- The role-scoped state machine in `blackboard-update.ts` rejected an
  Executor attempt to publish `ready_for_acceptance` (which is a
  Reviewer-only state per `ROLE_STATES`). The
  `blackboard_update(...)` call returned
  `state: must be equal to constant` / `state: must match a schema in
  anyOf`, which is exactly the protocol invariant: an Executor cannot
  impersonate a Reviewer handoff through the Blackboard. The
  `READY_FOR_ACCEPTANCE` signal travels to the paired Reviewer through
  the dedicated `pi_team_intercom` channel instead, preserving the
  Reviewer ownership of the lead-facing acceptance evidence.
- The 240-character activity cap (per `Type.String({ maxLength: 240 })`
  in the tool schema and the `ensureLineField("activity", …, 240)`
  check in `blackboard-core.mjs`) rejected an over-long activity
  string. The retry with a tightened `activity` was accepted. The
  protocol's hard length boundary is enforced both at the tool
  boundary and at the storage layer, so a future caller cannot bypass
  it by invoking `appendAgentEvent` directly.

## Reviewer feedback addressed

- `REVIEW_FAIL` for `ISSUE006-001` —
  `failures/ISSUE006-001-read-previous-event-cross-role.md`.
  Root cause: `readPreviousEvent` used
  `listAgentEvents(stateRoot, taskId, { limit: 1 })`, which returns only
  the single most recent event across all three role files. When that
  event belonged to another role, the loop had no role-local event to
  return, and the verbatim-repeat anti-heartbeat guard in
  `validateAgentUpdate` was silently disabled.
  Fix: `readPreviousEvent` now reads a 500-event window, filters by
  the requested `role`, and returns the highest-`sequence` matching
  event while honoring the optional `currentSequence` cursor. The
  Reviewer-authored regression test (now in
  `tests/blackboard-protocol.test.mjs`) passes against the fixed
  implementation.
- All four acceptance criteria remain satisfied. The new test
  (test 16 in the count below) is the cross-role regression added
  by the Reviewer; it is now part of the deterministic suite and
  will catch any future regression of the same shape.

## Design summary

### Lifecycle checkpoints

Each role has a fixed map from role state to lifecycle checkpoint:

- researcher: start/progress = `working`; blocked = `blocked`;
  handoff = `completed`; waiting = `waiting`.
- executor: start/progress = `working`; blocked = `blocked`;
  handoff = `ready_for_review`; waiting = `waiting`.
- reviewer: start/progress = `reviewing`; blocked = `blocked`;
  handoff = `ready_for_acceptance` or `changes_requested`;
  waiting = `waiting`.

The Lead therefore always sees the role in a named phase of the pair
lifecycle and never has to guess.

### Field semantics

- `activity` is the observed fact. Rejects placeholders (`ok`, `done`,
  `still working`, `tbd`, …) and verbatim repeats of the previous event.
- `blocker` is mandatory whenever the state is `blocked` or
  `changes_requested`; other states must not carry a `blocker`.
- `next` is mandatory for every non-terminal state except
  `ready_for_review`, `ready_for_acceptance`, `changes_requested`, and
  `completed`.

### Bounded lifecycle gate

The extension registers a `tool_call` handler. It blocks the first
substantive tool call until a `blackboard_update` is published; after
that, it blocks every 20 substantive tool calls that pass without a
further update. The bypass counter is hard-capped at 2. After that, the
gate fails *open* and records the bypass in its history. The
compression extension's terminate-on-resource-cap is unchanged; the
Blackboard gate never terminates the session, so it cannot recreate the
previous ISSUE-006 compression-unit crash.

- Blackboard remains an observation plane. The protocol module and the
  extension never import `pi_team_intercom`, `contact_supervisor`, or
  any `acceptTask`/`reconcileTask`/`archiveTask`/`closeIncompleteTask`
  path. A structural negative test (test 12) enforces this on disk.
- The compression extension is unchanged. No edit touches
  `.pi/communication/extensions/compression.ts`,

- The previous blackboard contract (Lead-only task mutation, append-only
  event log, wakeup dedup, `blocker` field) is preserved; the new
  constraints only reject *what an Agent is allowed to publish*, never
  *what Lead can read or archive*.
- The previous tests in `tests/blackboard.test.mjs`,
  `tests/team-contract.test.mjs`, and

  small "tests directory contains …" allowlist update that registers

- Reusable content is task-agnostic. The role prompts and skills only
  describe the protocol; they contain no task IDs, issue numbers, host
  paths, or worktree references.

## Remaining risks

- The bounded gate fails open after 2 bypasses. A misbehaving role that
  publishes a meaningless update could in principle satisfy the gate
  while still masking progress. The semantic validation rules
  (placeholder refusal + verbatim-repeat refusal + required `next`)
  cover this, and the gate history is observable to Lead, but the
  final defense is the Reviewer's re-review of the appended events.
- The protocol is enforced at the `blackboard_update` boundary. If a
  future extension bypasses the tool, the constraint would not apply.
  The structural negative test pins the current import surface.
- The `readPreviousEvent` path opens one read per blackboard update.
  Each read calls `listAgentEvents` with a 500-event window; this is
  acceptable because updates are infrequent and the operation is
  bounded by the file lock and the global event cap.
