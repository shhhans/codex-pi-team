# Architect Memory

## Accepted decisions and rationale

- **Hub-and-spoke + bounded peer** is the default-correct topology for this Pi-based team. **Lead = Codex (user-facing session), not a Pi subagent.** Codex owns canonical state on the routine path. `contact_supervisor` (closed enum of reasons) is the escalation channel for subagents; `intercom send` is the peer channel. Routine completion returns through `pi-subagents`, not `contact_supervisor`. (Source: `.pi/decisions/2026-08-21-agent-team-communication-baseline.md` items 1, 6; `.pi/research/agent-team-communication-architecture.md` §1, §3, §9.)
- **Per-decision accountability** (RACI single-A) is preferred over per-agent accountability. Every decision has exactly one `A`; conflicts resolve by precedence rule `User > Lead > domain-specialist-on-domain > domain-specialist-off-domain > most-recent-writer` (subject to user confirmation, baseline D-1).
- **Decision log is append-only** at `.pi/decisions/<YYYY-MM-DD>-<slug>.md`. Never edit past entries; new decisions that contradict must declare `supersedes:`.
- **Message envelope** deliberately omits application-level hashes/merkle roots. Identity, correlation, timestamps, sender, recipient, kind, references only. **Idempotency = ONE UUID generated at origination, reused for every retry of that logical request** (baseline item 8). Do NOT derive idempotency identifiers from payload hashes, content hashes, or `(sender, intent, plan_version)` tuples.
- **Tamper detection on decision log = ordinary git history review.** Use `git log`, `git diff`, and human inspection. No cryptographic claims, no WORM claims, no hash-chain claims (baseline correction; replaces any mtime-based or crypto claim).
- **Lead-to-User communication is ordinary Codex conversation**, not an intercom channel, not a `contact_supervisor` call, not a subagent tool call (baseline correction).
- **`contact_supervisor.reason` is closed** at exactly three values: `need_decision`, `progress_update`, `interview_request` (verified from `node_modules/pi-intercom/index.ts` line 1543 — `StringEnum(["need_decision", "progress_update", "interview_request"] as const)`). Do not invent new members; use a structured `interview` payload field for `interview_request` and a freeform `message` field for the other two.
- **No undocumented transport fields.** `priority: blocking` and `reply_path: live` are NOT in the baseline and must not appear in v2. v1's blocking paths are replaced by `intercom({ action: "ask", ... })` (the only blocking peer primitive) and `contact_supervisor({ reason: "need_decision", ... })` (the only blocking supervisor primitive).

## Current verified policy (runtime-wiring and authorization)

- **Intercom is runtime-wired through role extensions, not declared in the `tools:` field as the source of registration.** Each role that uses intercom registers a `subagentOnlyExtension` under `.pi/communication/extensions/<role>.ts` (e.g., `architect.ts`, `critic.ts`, `researcher.ts`). Some agent files also list `intercom` in `tools:` as a contract hint, but the binding that the action is callable comes from the extension, not from the YAML list. Editing the `tools:` line is therefore not sufficient to wire a role to intercom; the extension file is the source of truth.
- **Critic and Reviewer may use `contact_supervisor` only with `reason: "need_decision"`.** This is enforced by `authorizeSupervisorEscalation(sender, reason)` in `.pi/communication/policy.mjs`, which returns true iff `sender ∈ {critic, reviewer}` AND `reason === "need_decision"`. The read-only `acceptanceRole` does not exclude `contact_supervisor`; it excludes write/exec tools. Architect, Engineer, and Researcher also have `contact_supervisor` but use the full closed reason set per their role prompts (Lead-mirror via `progress_update`, `need_decision`, `interview_request` as appropriate; routine completion still returns through `pi-subagents`).
- **Bounded peer authorization is Agent policy and Lead audit, NOT a transport ACL.** The role prompts (architect/critic/researcher) instruct the Agent to refuse before invoking `intercom send` or `ask` to a non-bounded peer, and to route through Lead. `LeadAudit.record({ sender, recipient, action })` in `.pi/communication/policy.mjs` is the compliance record — every allow/deny is logged for the Lead. `refusalTrace(...)` produces the refuse-before-intercom trace that the Agent-side enforcement relies on. The transport may independently refuse via `MessageQueue.enqueue` → `authorizePeer`, but the canonical model is: Agent refuses first, then Lead audit records, transport is the last line. This is the established interpretation; do not relabel bounded peers as a transport ACL.

## Stable constraints and boundaries

- **Installed substrate (verified from `.pi/settings.json`):** `npm:pi-intercom@0.11.0`, `npm:pi-subagents`, `npm:pi-web-access`. No pub/sub, no blackboard, no external Kafka/Redis topic. Architecture must not propose tools not in this set.
- **Agent definitions** at `.pi/agents/` (architect, critic, engineer, researcher, reviewer) are authoritative and IMMUTABLE for design exercises. They declare tool surfaces. The Lead is NOT defined as an agent file — Lead is the user-facing Codex session.
- **Verified agent tool surfaces and extensions (current):**
  - architect: `read, grep, find, ls, write, contact_supervisor, intercom` — extension `../communication/extensions/architect.ts`. Bounded peers: `researcher`, `critic`. Lead mirror via `contact_supervisor({ reason: "progress_update", ... })`.
  - critic: `read, grep, find, ls, contact_supervisor, intercom` — extension `../communication/extensions/critic.ts`. `acceptanceRole: read-only`. `contact_supervisor` ONLY with `reason: "need_decision"`. Bounded peer: `architect` only.
  - engineer: `read, grep, find, ls, bash, edit, write, contact_supervisor` — extension `../communication/extensions/engineer.ts`. NO intercom in tools; no direct peer channel during initial rollout.
  - researcher: local inspection plus `research_run`, controlled `deep_research_task`, `deep_research_review`, clean synthesis/report tools, `contact_supervisor`, and `intercom`; no direct web search/extract. Deep Research is an external MCP capability. Bounded peer: `architect` only.
  - reviewer: `read, grep, find, ls, contact_supervisor` — extension `../communication/extensions/reviewer.ts`. `acceptanceRole: read-only`. `contact_supervisor` ONLY with `reason: "need_decision"`. NO intercom; no direct peer channel during initial rollout.
  - **Runtime wiring source of truth = `subagentOnlyExtensions`.** A `tools:` line that lists `intercom` is a contract hint, not the registration mechanism. To wire (or re-wire) a role to intercom, the extension file under `.pi/communication/extensions/` is what must be present and loaded.
- **Read-only roles (Critic, Reviewer):** enforced by `acceptanceRole: read-only` and absence of write/exec tools in their definitions. They cannot edit files, run shell, or use write/exec tools. **They DO have `contact_supervisor`** — restricted to `reason: "need_decision"` for risk or verdict escalation, never for routine completion (per role prompts and `policy.mjs` `authorizeSupervisorEscalation`). Critic additionally has `intercom` (bounded to Architect). Reviewer has no direct peer channel and routes everything through Lead.
- **`contact_supervisor` registration:** the tool is supplied when `pi-subagents` provides child bridge metadata. Normal parent Pi sessions do NOT see `contact_supervisor`. The tool surface visible to each role is the union of (a) what the role's `tools:` line declares and (b) what the role's `subagentOnlyExtensions` register. Read-only roles with `contact_supervisor` in tools (critic, reviewer) see it because `pi-subagents` registers it for the child session — `acceptanceRole: read-only` does not strip it.
- **`intercom` actions available** (verified in `node_modules/pi-intercom/index.ts` line 1827 — full enum): `list`, `list-cwd`, `send`, `ask`, `reply`, `pending`, `status`, `cancel`. The project's `AGENTS.md` codifies the async pattern: requester uses `send` (non-blocking), response is a second `send` carrying the originating message id in text for correlation.
- **`intercom({ action: "ask" })` is the only blocking peer primitive.** `reply` resolves pending `ask` requests only — it does NOT resolve `send` requests (AGENTS.md).
- **Evidence-quality defect (MEDIUM):** `agent-team-communication-report.md` claims 15 sources but contains 26 unique URLs. Any numeric or adoption claim inherited from that report must be qualified as "report states X, evidence quality MEDIUM, treat as directional". Never propagate the report's 90% confidence figure forward as a derived conclusion.

## Unresolved risks

- **MEDIUM.** Lead's `intercom` handle / session-id convention is not codified. Codex Lead does not currently have an `intercom` tool registered (Lead is a Codex session, not a Pi session). The Lead's role in intercom is as a peer reachable from Pi subagents IF a Pi session nominates Codex as a peer and a runtime receiver is wired in. The extension mechanism that would do this is the same `subagentOnlyExtensions` path used for the other roles, but no such extension file exists for Lead today. v2 must specify whether Lead participation is via a Lead-side extension, a Codex-side receiver, or remains out-of-band.
- **MEDIUM (revised).** Critic and Reviewer escalation paths are now partially wired but uneven. Critic has both `contact_supervisor` (`need_decision` only, per `policy.mjs`) and `intercom` (bounded to Architect only); Reviewer has `contact_supervisor` (`need_decision` only) but NO `intercom`. Asymmetric coverage is by design (Reviewer routes through Lead), but it means Reviewer's only escalation surface is `contact_supervisor({ reason: "need_decision", ... })` — there is no intercom fallback for Reviewer. v2 should record this asymmetry as intentional, not as a gap to close.
- **MEDIUM.** `pi-subagents` and `pi-intercom` are community packages; their reason enums and tool surfaces may evolve. The installed `contact_supervisor.reason` enum is verified today (`need_decision | progress_update | interview_request`); architecture must pin against it.
- **LOW.** No demonstrated UX for `contact_supervisor interview_request` in this project — whether the user answers structured multi-option interactively or as freeform prose is unclear.
- **LOW.** Conflict-resolution precedence rule (`User > Lead > domain-specialist-on-domain > domain-specialist-off-domain > most-recent-writer`) is principled, not empirically validated against real cross-cutting decisions in this project. Pending user choice D-1.
- **MEDIUM (revised; was HIGH in v2 draft).** Intercom exposure to Critic is now runtime-wired via `.pi/communication/extensions/critic.ts`. The remaining runtime gap is NOT "Critic/Reviewer cannot use intercom at all" — that claim is stale. The remaining gap is (a) Lead-side intercom participation (see first MEDIUM item), and (b) whether `MessageQueue.enqueue`'s transport-side `authorizePeer` check should be treated as part of Agent policy enforcement or as a defense-in-depth backstop (canonical answer per current policy: backstop; primary enforcement is Agent refusal + Lead audit). v2 should codify the backstop-vs-policy interpretation explicitly.
