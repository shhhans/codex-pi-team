# ADR 0009 — Persistent module groups and durable handoffs

Status: Accepted by user design decisions; bounded local deterministic and real-role verification recorded in project_state.md.
Date: 2026-10-19 (updated 2026-10-20)
Supersedes active workflow and interface rules in ADR 0002, 0003, 0005, 0007 and 0008. Their historical evidence remains intact. Explicit user development and recovery instructions remain authoritative.

## Decision

A group owns one module, one fixed Git worktree and three role identities: Coordinator, Executor and Validator. Tasks are serial within a group and may run in parallel across groups. Lead owns group definitions, external objectives, module boundaries, scope changes, acceptance and integration. Coordinator owns task coordination and external communication, including Coordinator-to-Coordinator contact. Executor implements and plans when assigned. Validator performs one adversarial plan review only on the review route, reviews each code delivery, and receives a separate module-documentation alignment assignment after code review passes.

### Definition and onboarding lifecycle

The project file `groups/<id>/group.md` is the durable group configuration and registration source. It has YAML front matter with `schema_version: 1`, `id`, `name`, absolute `worktree`, `base_ref` and optional `archived`, followed by a nonempty Markdown description of module responsibilities. The directory name must equal `id`. Runtime records are recoverable projections; a valid file alone does not prove that role sessions are running. Lead is the only role that edits and commits group definitions. Task startup requires the current definition to be committed in the target project.

`group-create` / `team_group_create` creates the fixed worktree, writes the definition and schedules finite onboarding. It starts real Executor, Validator and Coordinator sessions, but no persistent business task. Executor and Validator each submit an explicit `kind=onboarding` acknowledgement for the assigned module and role. Coordinator cannot acknowledge until it has both peer receipts, then submits its own acknowledgement for Lead. A successful stored receipt proves that role's acknowledgement; messages, startup or a model's prose do not. The onboarding runner stops all three sessions. No module implementation or open-ended business work is authorized by onboarding. Lead commits the generated definition before task startup; `group-init` / `team_group_init` is an explicit retry after inspecting an onboarding fault.

`group-update` / `team_group_update` changes the desired definition. If a task is active, application is deferred until that task reaches a safe boundary. Applying the definition stops old role processes and managed child commands, archives prior session records, clears all three session registrations, increments the definition epoch and requires fresh Executor, Validator and then Coordinator acknowledgements. Session state from the prior definition is not copied into the new sessions. The group keeps its fixed worktree. Lead commits configuration in the target project. `group-sync` / `team_group_sync` fast-forwards only a clean idle group worktree from a clean committed Lead checkout. Task finalization also fast-forwards the target branch into the worktree's idle branch after integration.

### Task and evidence workflow

Lead assigns at most one active task to a group. The task carries an objective, observable acceptance results, base ref and optional explicit module Markdown `documentation_paths` plus an observable `documentation_checklist`. Documentation paths are relative Markdown paths outside `groups/` and `.git/`; paths must exist as regular files inside the worktree and cannot traverse symlinks. Runtime can commit only the explicitly delegated documentation prose with an empty index, preserving production changes and unrelated staged content.

Coordinator declares task_type=non_change, small_change, or large_change on initial team_submit(kind=task), records a short reason in task.md, and preserves it after submission. Non-change tasks modify only their own task records, analysis or review artifacts; product code, tests, configuration and module documentation remain unchanged. Small changes are bounded with a known solution; large changes involve material design/interface/state/concurrency/recovery/compatibility risk. Judge impact and uncertainty, not line count. Defaults are direct for non-change/small changes and review for large changes; plan remains available for design uncertainty. Classification never expands Lead scope.

Coordinator submits task.md with an optional planning route: direct opens implementation immediately; plan requests a plan then implementation; review requests a plan and exactly one Validator plan review. Omission preserves review for compatibility. Coordinator chooses proportionately, records the reason in task.md, and cannot widen Lead scope. Missing plan artifacts on direct tasks are not defects. Unexpected uncertainty may be discussed through team_send; final independent code and documentation reviews remain required. On the review route, Executor submits plan.md and Validator submits exactly one plan-review.md. The plan review is adversarial advice, not an approval or ACK gate. Executor records concern adoption or rejection in implementation.md and proceeds without a second plan-review round. Genuine blockers go to Coordinator. Material objective changes require a new Lead-owned task.

For classified tasks, Validator checks the exact delivery commit, source/diff and acceptance evidence in one code-review-NN.md. For non_change, verify no base-to-delivery changes outside the task directory; mismatch is blocked for Coordinator/Lead resolution, never silently reclassified. For change tasks, review code/tests first, then check the documentation checklist and align only explicitly delegated module Markdown or explain no change. On passing code_review, runtime commits only authorized Markdown, binds code/documentation commits to the combined review and opens Coordinator delivery directly. There are no separate documentation or Coordinator documentation-review reports. Coordinator checks acceptance, exact version bindings and unresolved issues while preparing delivery.md; Lead alone accepts and integrates. Each fix needs a new delivery and independent review. Existing tasks/callers omitting task_type retain the legacy separate documentation/alignment-review stages and artifacts; no automatic migration.

### Runtime authority and communication

Runtime authority is SQLite below `<git-common-dir>/pi-team-runtime/v2`. Document content snapshots, work completion and successor creation are transactional. Documents are authored first; `team_submit` is the handoff. Writing a file or sending a message does not complete work. The runtime injects role/task/definition identity and binds mutations to the current session and owned `work_id`. Successful submissions return an explicit receipt; rejected submissions never imply completion. Human-readable IDs belong in artifacts; Git object IDs bind code versions.

The group extension exposes `team_read`, `team_send`, `team_submit`, and Coordinator-only structured `team_service`. The Lead MCP exposes `team_groups`, `team_group_create`, `team_group_update`, `team_group_init`, `team_group_sync` plus durable message and acceptance/finalization tools. Three roles within a group may communicate directly; only Coordinator contacts Lead or another group. The `[current_state: "description"]` prefix is best-effort display only. Blackboard lifecycle state, formal debate and contract ACK gates are retired; finite group onboarding acknowledgements are separate and required. Lead has durable inbox and bounded wait tools, with no autonomous desktop-chat wakeup.

A provider/model-only configuration migration is a narrow exception to fresh onboarding. Lead may run `group-provider-migrate <group> <exact-prior-roles-json>` after all three role processes stop. The operation verifies the exact prior role version against current prompt and skill files, checks the full role configs and permits differences only in provider/model, and checks recorded process identities. It preserves active task/work, session IDs, conversation paths, onboarding receipts and definition epoch, and records the prior source and prior session records in a durable SQLite migration receipt. Verified PID reuse is recorded and detached from the stale registration without killing the unrelated process. Live matching or unknown process identities reject migration. Role-config differences are limited to provider/model; old PID registrations and provider fault markers are cleared. A resume notice goes only to roles with open work; unassigned roles receive no migration-only wakeup, while existing peer messages remain available normally. No onboarding acknowledgement is emitted. Tool, skill, prompt or responsibility changes still require normal `group-init` onboarding.

Messages have separate presented and settled timestamps. New messages steer work at safe tool boundaries; a same-batch mutation waits for the next model response. Submission rejects unpresented inbox arrivals. A model stop does not complete open work: unfinished assignments and unresolved tool rejections create durable, deduplicated alerts, and incomplete reviews open Coordinator resolution work. Recovery re-discovers work without model polling.

### Services and project integration

Coordinator may describe, start, inspect status for, and stop a named service from the target project's `.pi/services.json`. A managed service definition uses an executable and string argument array, optional worktree-relative `cwd`, environment variable references (`env_refs`), declared ports, and an optional loopback HTTP health URL. An external dependency may instead set `external: true` and provide a description with an optional loopback health URL; it is displayed as `owned: false`, and start/stop are refused. If a service becomes external while its prior manager-owned process is still live, the exact PID-verified runtime record remains visible and can be stopped to avoid orphaning it. Free-form shell commands and inline environment values are rejected. Development mode uses the group worktree. Review mode requires a registered delivery commit, exports that commit to an isolated read-only snapshot and checks snapshot integrity before reporting readiness. Runtime records process identity and owns explicit stop operations; port conflicts between declared managed services are rejected. The explicit service-lock recovery action removes a lock only when its recorded process owner is proven dead or the PID has been reused; live or unreadable locks remain for inspection.

`.pi/project.json` declares the target integration command using `integration.executable` and `integration.args`. Lead finalization requires an accepted delivery and clean target branch, stops group-managed services, merges the reviewed branch (concurrent Lead group-definition changes and unchanged process files from other groups' accepted, fully finalized tasks are allowed), runs that configured command, and returns the fixed worktree to its idle branch. Process-file exceptions are limited to paths recorded for the completed task and must still match that task's finalization commit. A failed integration check after merge is retained for inspection and retry; a skipped command is not evidence that integration tests ran.

Three role sessions may remain allocated between tasks once the group is in use, but group creation itself does not authorize persistent business work. Finalization preserves the fixed worktree and session history; an updated definition is the explicit boundary that resets all role sessions. Incomplete branches and evidence are retained. No active v1 task is migrated; cutover requires explicit completion or closure using the old checkout.

## Enforcement boundary

### Reviewed joint integration

Parallel tasks may share a Lead-owned `integration_id` and exact baseline while retaining distinct task identities and independent three-role workflows. Cross-group Coordinator messages bind pending delivery to the receiver's current task and retain the sender task separately. A reviewed joint candidate records the member tasks, exact code/documentation commits, candidate commit/tree and independent verification group. It does not authorize merging arbitrary task branch tips.

The independent evaluation task must bind its `verification_snapshot` to the exact candidate integration ID, commit and tree. Final integration requires Lead acceptance of the members and that evaluation, unchanged reviewed evidence, candidate integrity and a clean unchanged Lead baseline. Mandatory declared integration tests run before the target advances. Task branches, worktrees and evidence remain recoverable; failure and retry do not establish successful completion. The existing single-task target-drift guard remains in force.

Tool wrappers restrict obvious writes and stage-dependent operations, but do not form a shell sandbox. Validator may inspect production source and run tests but may not edit production code. During classified change-task review or legacy documentation work, Validator may edit only explicitly delegated Markdown module files; its conclusion belongs in the assigned review report. On a failing review, leave module prose unchanged. Runtime validates documentation paths and commits only listed prose. Git and evidence checks reject drift before review, documentation-review and Lead acceptance. Transport receipt is not proof that a message affected work; inspect resulting artifacts and revisions.

## Verification boundary

This ADR records the chosen protocol, not a claim that the latest implementation or cutover is accepted. Keep deterministic suite results, isolated-copy real-provider evidence, original-project provisioning and remaining live-provider checks distinct. Do not infer original-project deployment, long-term module maintenance, or validation of later error-handling changes from earlier runs. The current implementation remains under verification.

## Runtime context and shared knowledge

Runtime injects authoritative versioned work cards, artifact paths, exact delivery/documentation commits and relevant messages before work and in steering notifications. Stable contracts appear once per context version in durable session messages. A complete notification permits action without an extra team_read call. Read referenced task/review documents before acting. Use team_read for missing context, rejection, restart or compaction recovery (refresh_context:true); shared_context:true explicitly retrieves published team knowledge. No work means end idle. Submission identity, stale-turn checks and message handling still apply.

Coordinator writes task.md before initial dispatch and preserves it after submission. Later decisions use messages or assigned decision artifacts. Choose direct for known bounded changes, plan for coordination/design uncertainty, review for substantial state/concurrency/recovery/compatibility risks. Extra verification needs a concrete risk, new assumption or failed result. Existing independent code/documentation reviews and Lead acceptance remain required.

Coordinator maintains cross-task shared knowledge in a concise replacement section headed exactly `## Shared knowledge` in delivery.md (maximum 6000 characters), with source references. Submit delivery with shared_context:{mode:"update"}, or reuse the current published version with {mode:"reuse",version:N}. Omission remains compatible and publishes nothing. Runtime freezes content, hash, definition epoch, source task/path and code commit with the delivery. Lead checks changed knowledge in existing acceptance. SQLite publishes a version and integration commit only when accepted finalization succeeds, including joint integration; retries are idempotent. Failed, incomplete or rejected tasks publish nothing. Notifications carry a pointer; retrieve content only when relevant. History is retained; a definition epoch change requires fresh knowledge before it is current. Role continuation uses existing automatic compaction.
