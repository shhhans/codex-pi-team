# ADR 0007 — Lightweight v3 task contract

Status: Accepted
Date: 2026-09-09

## Context

The previous task contract combined task intent, file scope, role prompts,
capability declarations, artifact ownership, lifecycle instructions, and
acceptance evidence. Natural-language scope was too ambiguous to enforce
deterministically and made role prompts harder to follow.

## Decision

New tasks use a Markdown contract containing one JSON `version: 3` block with:

- task identity: `task_id` and `name`;
- `objective`;
- optional explanatory `context` strings;
- two to five observable `acceptance` result strings;
- explicit `base_ref`, `branch`, and `worktree`;
- optional `deliverables` labels.

The contract does not contain file scope lists, role delegations, capability
lists, criterion owners, or artifact mappings. Executor, Reviewer, and
Researcher runtime assignments are generated by the launcher from the stable
role cards. Research requests receive generated runtime IDs and conventional
artifact paths.

`inspect` reports facts. The Lead decides whether actual changes satisfy the
objective or are out of scope. `accept` records one Lead decision with a
rationale and optional inspect reference. `finalize` executes the accepted
decision and does not re-evaluate semantic scope.

`base_ref` is also the default finalization target. A different target requires
the explicit Lead `--target-branch` override, which is frozen for retries.

## Consequences

Task contracts are shorter and easier for roles to follow. Lead judgment is
preserved where natural-language intent cannot be reduced to a safe path
allowlist. Hard Git, test, process, and credential safety checks remain
deterministic. Historical v2 contracts are retained as historical artifacts;
they are not automatically migrated or started as v3 tasks.
