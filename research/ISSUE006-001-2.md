## Question (one sentence)

Across the three active roles (Researcher, Executor, Reviewer), which Blackboard
lifecycle nodes are currently mandatory vs. self-disciplined in the develop branch,
what is the minimum executable protocol that satisfies GitHub Issue #6's required
nodes (start slice, key progress, blocked, completed, waiting, long-work updates)
without making Blackboard a control bus, and what concrete modifications increase
Lead observability while preserving the observation-only boundary?

## Headline answer (1–3 sentences)

1. **The Blackboard state machine and tool surface already cover Issue #6's
   required nodes; the gap is role-protocol discipline, not missing states.**
   `ROLE_STATES` (`plugins/agent-blackboard/server/blackboard-core.mjs:7-11`) plus
   `LEAD_WAKE_STATES` (`blackboard-core.mjs:13`) and the `blackboard_update` tool
   schema (`.pi/communication/extensions/blackboard-update.ts:32-38`) admit exactly
   the required nodes (`working` / `waiting` / `blocked` / `ready_for_review` /
   `reviewing` / `changes_requested` / `ready_for_acceptance` / `completed`); the
   per-role markdown workflows already prescribe `working` before first tool call,
   `waiting` / `blocked` between slices, and `ready_for_*` / `changes_requested` at
   slice boundaries (`.pi/agents/researcher.md:13`, `.pi/agents/executor.md:13`,
   `.pi/agents/reviewer.md:13`).
2. **The minimum executable protocol is a tightening of when each role emits
   which state, plus a single positive regression test per role that locks the
   contract.** Concretely: each role must emit one `working` event at the start of
   every slice (with `activity` = slice objective and `next` = next milestone),
   must emit `working` (not `waiting`) at material phase boundaries inside a
   long slice, must use `blocked` (with non-empty `blocker` and `next`) when
   blocked on external input and `waiting` only when truly idle, and must emit
   the canonical slice-end state (`ready_for_review` / `ready_for_acceptance` /
   `changes_requested`). No new states are needed; no control fields are added
   to the schema.
3. **The observation-only boundary is already enforced by the Blackboard
   architecture** (`ADR/0005-agent-blackboard-observability.md`, the
   `blackboard_update` schema with no `command` field, the `inspect` path as the
   Lead evidence source, and the heartbeat snapshot cursor pattern in
   `plugins/agent-blackboard/skills/{blackboard-lead,pi-team-lead}/SKILL.md`).
   The cleanest increase in Lead observability is therefore (a) make the slice
   events above deterministic, (b) record them in regression tests that assert
   both the sequence AND the absence of any non-observation control payload,
   and (c) expose `lead_wakeup_pending` / per-agent latest state through the
   existing `blackboard_snapshot` so Lead heartbeat polling does not need a
   separate read path.

### 1.4 Blackboard wakeup semantics are asymmetric across roles and states

- **Source.** `LEAD_WAKE_STATES = {"blocked", "changes_requested",
  "ready_for_review", "ready_for_acceptance", "completed"}`
  (`blackboard-core.mjs:13`).
- **Source.** `appendAgentEvent` only enqueues a wakeup when the state is in

- **Source.** `snapshotChanges` only emits change entries for states in

- **Implication.** `working`, `waiting`, and `reviewing` are observed by Lead

- **Implication for Issue #6.** Issue #6's "key progress" and "waiting" are

  the wakeup or `changes` channels. The protocol design must accept that
  these nodes are *cooler* signals than the wakeup-eligible states; they
  still matter for the snapshot but do not wake the Lead.

## 2. Inferences (unverified; for Lead review)

- **I1.** The reason Issue #6 reports long Blackboard lag is not that the
  Blackboard state machine is missing, but that the role workflow text is
  self-enforced and has no test coverage. When the model "forgets" to publish
  a slice event, there is no test failure, no alarm, and the Lead has no
  signal until the next LEAD_WAKE_STATES event arrives (or never, if the
  role sits in a non-wakeup state such as `working`). **Inferred from the
  Issue #6 text + the existing tests; not directly proven.**
- **I2.** The protocol's natural unit of "long work" is the slice, not the
  wall clock. A "long slice" is one that has emitted at most one `working`
  event and no phase-change event for an extended wall-clock interval. The
  natural remedy is not a heartbeat (explicitly forbidden) but a "phase
  progress" event: when the role reaches a meaningful internal milestone
  inside a slice, it should append another `working` event with the new
  `activity` and `next`. The semantics match `executor.md:13` "update it
  again when beginning a concrete phase" and `researcher.md:13` "update it
  when changing research phase" — these are already in the role prompts;
  Issue #6 only needs to require they happen on every material phase change,
  not on a clock. **Inferred from the existing role text.**
- **I3.** Issue #6's "Lead can intervene, re-review, and accept based on
  stale state" maps cleanly to the wakeup-eligible state set plus the
  snapshot's per-role latest event. Once the role workflow is tightened to
  emit `working` at slice start and at every phase boundary, the Lead's
  `inspect` and `blackboard_snapshot` paths already carry enough
  information to distinguish "the role is making progress" (`working`
  recent, activity text advancing), "the role is idle" (`waiting`
  recent), "the role is blocked" (`blocked` with `blocker`/`next`),
  "the slice is complete" (`ready_for_review` / `ready_for_acceptance`),
  and "the role needs another pass" (`changes_requested`). No new schema
  field is required for any of these. **Inferred.**
- **I4.** The role-extension files (`.pi/communication/extensions/{researcher,
  executor,reviewer}.ts`) only install the role policy; they do not emit any
  Blackboard event themselves. Therefore any auto-emitted slice-event
  contract would need to live in either (a) the role markdown, (b) a
  shared helper invoked by the role, or (c) the `blackboard-update.ts`
  extension's lifecycle (e.g., a synthetic "ready" event when the extension
  loads). Option (c) is the only place a "I am ready" sentinel could be
  emitted automatically without role discipline, but it would add coupling
  between the extension and the role. **Inferred.**
- **I5.** The existing `tests/blackboard.test.mjs` "critical Agent events
  enqueue a bound Lead wakeup…" already implicitly relies on the role's
  emitted `activity` carrying semantic content. The wakeup digest
  (`formatLeadWakeup` in `lead-wakeup-adapter.mjs:101-130`) uses
  `activity` as the human-readable summary. A role that emits `working`
  with `activity: "..."` containing the slice objective is the prerequisite
  for the wakeup prompt to be useful. **Inferred; the wakeup adapter
  reads `activity` directly (`lead-wakeup-adapter.mjs:117-118`).**
- **I6.** Adding "long work" semantics by adding a new Blackboard state
  (e.g., `progress`) would be the wrong move: it would expand `ROLE_STATES`
  for every role, require a new `LEAD_WAKE_STATES` decision, and require
  re-deciding whether `progress` is wakeup-eligible. The current state set
  is intentionally minimal; "long work" should be expressed as repeated
  `working` events with advancing `activity` text. **Inferred from the
  shape of `ROLE_STATES` (4 states for Researcher, 4 for Executor, 6 for
  Reviewer; all already used).**

## 4. Suggestions (proposed minimum protocol; Lead decides)

### 4.1 The protocol (text-only, no new code)

A role-emitted Blackboard event **MUST** satisfy one of the following
contracts. The contracts map to Issue #6's required nodes.

| Node (Issue #6)            | State                | Required payload                                                       | Frequency                                   |
|----------------------------|----------------------|------------------------------------------------------------------------|---------------------------------------------|
| Start slice                | `working`            | `activity = "start <slice>: <objective>"`, `next = "<first milestone>"` | exactly once per slice (role's first event) |
| Key progress               | `working`            | `activity = "<phase>"`, `next = "<next milestone>"`                    | every material phase boundary inside a slice |
| Blocked (external input)   | `blocked`            | `blocker = "<what is blocking>"`, `next = "<what unblocks>"`           | whenever the role stops on external input   |
| Waiting (idle)             | `waiting`            | `activity = "<what is being awaited>"`                                  | end of every turn where the role is idle    |
| Slice complete (Executor)  | `ready_for_review`   | `activity = "<slice summary>"`, `next = "<awaiting review>"`           | exactly once at slice end                  |
| Slice complete (Reviewer)  | `ready_for_acceptance` / `changes_requested` | `activity = "<verdict>"`, optional `next`         | exactly once at review end                 |
| Slice complete (Researcher)| `completed`          | `activity = "<artifact delivered>"`                                     | optional, on Lead-driven reclamation only   |
| Long-work update           | `working`            | `activity` and `next` reflect new phase, not wall clock                 | at least once per "phase" inside long slice |

A role **MUST NOT**:
- emit the same state more than once per slice without an intervening
  state transition or a new `activity` / `next` text (the "no heartbeat"
  rule),
- emit `working` with `activity` text that does not advance between events
  within the same slice (forces phase-progress discipline),
- emit any state outside `ROLE_STATES[<role>]` (schema enforces this),
- emit a `blocker` field on a non-`blocked` state (schema-agnostic, but
  workflow should enforce), or
- emit a `next` field on a `waiting` state (a `waiting` role's "next" is
  not the Lead's decision; the Lead reads the wakeup to know what to do).

The **Lead wakeup behavior** stays as-is: only the `LEAD_WAKE_STATES` set
enqueues a wakeup; `working` / `waiting` / `reviewing` are visible only
through the per-task `agents[<role>]` projection in `blackboard_snapshot`.

### 4.2 Where the protocol lives

- **Role markdown** (`.pi/agents/{researcher,executor,reviewer}.md`):
  add a single dedicated subsection "Slice event contract" that names the
  table above verbatim and cross-references the section below. The current
  Workflow bullet about "Do not use it as a heartbeat" stays; the new
  subsection supplies the "what to do instead" guidance.
- **Role skills** (`.pi/skills/{answer-research-question,execute-delegated-task,review-delegated-task}/SKILL.md`):
  add a "Slice events" subsection with the same table, plus role-specific
  examples (e.g., for Executor: "slicing a research-driven fix → start

### 4.3 Regression-test surface (proposed additions to `tests/blackboard.test.mjs`)

- **T1. Researcher slice contract.** Append three events
  `working(activity="start slice: …", next="…")`,
  `working(activity="phase 2", next="…")`,
  `completed(activity="delivered artifact at research/ISSUE006-001-X.md")`
  for a Researcher identity, then assert:
  - sequences are 1, 2, 3 (monotonic, server-assigned),
  - the first event's `activity` matches `^start slice:`,
  - the third event's state is `completed`,
  - the wakeup queue has entries for both `completed` events (i.e., only
    the wakeup-eligible states created wakeups, which here is just
    `completed`; `working` events produced no wakeup).
- **T2. Executor slice contract.** Append events
  `working(start slice: …, next=…)`,
  `working(phase 2, next=…)`,
  `ready_for_review(slice summary, next=awaiting review)`,
  then assert:
  - sequences 1, 2, 3,
  - the second `working` event's `activity` differs from the first
    (forces phase-progress discipline),
  - the wakeup queue has exactly one entry (`ready_for_review` is in
    `LEAD_WAKE_STATES`).
- **T3. Reviewer slice contract.** Append events
  `waiting(idle until review arrives)`,
  `reviewing(diff inspection)`,
  `ready_for_acceptance(verdict)`,
  then assert:
  - sequences 1, 2, 3,
  - the first `waiting` event is recorded even before any `READY_FOR_REVIEW`
    is received (initial idle discipline),
  - the wakeup queue has exactly one entry (`ready_for_acceptance`).
- **T4. Blocked carries blocker + next.** Append
  `blocked("waiting for Researcher evidence", "will resume after
  RESEARCH_RESULT arrives")` for an Executor; assert that
  `blocker` and `next` are both non-empty strings of length ≤ 500. Also
  assert `appendAgentEvent` with `blocked` and an empty `blocker` raises
  "blocker must be a single line of at most 500 characters" (or whatever
  the agreed negative contract is — currently the schema permits empty
  `blocker`; T4 is the place to lock the rule).
- **T5. Negative: command field cannot be smuggled in.** Read the
  `blackboard_update` schema source (`.pi/communication/extensions/blackboard-update.ts`)
  and assert that the `parameters.properties` keys are exactly
  `{task_id, state, activity, blocker?, next?}`. No new field may be
  added without breaking this test.
- **T6. Negative: lead-only MCP tools are not exposed to active roles.**
  Already covered by the existing "repo-local plugin exposes Lead-only
  tools…" test (the `for (const role of ['researcher', 'executor',
  'reviewer']) assert.doesNotMatch(... 'blackboard_create_task')` block).
  No change; reference only.
- **T7. Negative: heartbeat-style repeated working events are not
  evidence.** Append five `working` events with the same `activity`
  text and assert the role workflow contract would mark this as a
  regression (e.g., a docstring assertion on the role markdown). This
  test is purely on the markdown text, not on the runtime, because the
  runtime cannot distinguish "phase progress" from "heartbeat" — only
  the model can, and the markdown is what the model reads.

### 4.4 What increases Lead observability without changing the schema

- **O1. Use the existing per-role `latest event` projection.** The
  `blackboard_snapshot` result already exposes `agents: [{role, sequence,
  state, activity, blocker?, next?, observed_at}]` per active task. A
  tightened slice-event contract means each `agents[role].activity`
  carries the slice objective and each `agents[role].next` carries the
  next milestone; Lead heartbeat polling reads these directly.
- **O2. Surface `lead_wakeup_pending` count in the Lead heartbeat.**
  `blackboard-core.mjs:194` already exposes `lead_wakeup_pending`
  (`wakeups.filter(item => item.status !== 'acked').length`) on
  `taskSummary`. Lead can use this count to detect "wakeups piling up,
  role is not acking" without polling per-event. **Already implemented;
  Issue #6 only needs to make sure Lead heartbeat reads it.**
- **O3. Tighten the `inspect` path's Blackboard summary.**
  `scripts/pi-team.ps1:922-933` already lists
  `working / reviewing / ready_for_review / ready_for_acceptance / blocked`
  as warn-worthy states. With the slice-event contract in place, the
  `inspect` output will distinguish "role is mid-slice" (`working` with
  recent `observed_at`) from "role has been quiet for > N minutes"
  (`working` with stale `observed_at`), which the current `inspect` does
  not surface. Adding a `last_event_age_seconds` projection would make
  the observability concrete without a schema change.
- **O4. Do not add new states or fields.** The current state set and
  schema are intentionally minimal (`.pi/communication/extensions/blackboard-update.ts:32-38`);
  every Issue #6 requirement maps to existing fields. Any expansion of
  `ROLE_STATES` would force a `LEAD_WAKE_STATES` re-decision and would
  raise the regression-test surface area.

### 4.5 What keeps Blackboard observation-only

The boundary is already enforced by:
1. The `blackboard_update` schema has no `command` / `request` field
   (`.pi/communication/extensions/blackboard-update.ts:32-38`). **Test T5
   locks this.**
2. The active roles do not load the Lead-only MCP tools
   (`.pi/agents/{researcher,executor,reviewer}.md`'s `tools:` frontmatter,
   `tests/blackboard.test.mjs` "repo-local plugin exposes Lead-only tools…").
3. The Lead's `inspect`, `accept`, `request_changes`, `reclaim`, `archive`
   commands are launcher-owned (`scripts/pi-team.ps1`), not Blackboard-owned.
4. The Blackboard wakeup host adapter (`plugins/agent-blackboard/server/lead-wakeup-adapter.mjs`)
   produces only text prompts; the wakeup summary includes the literal
   "Action: inspect the current Blackboard snapshot, contract, diff, and
   artifacts before deciding the next Lead action." (`lead-wakeup-adapter.mjs:124`).
5. The Lead skills explicitly state the boundary
   (`plugins/agent-blackboard/skills/pi-team-lead/SKILL.md`: "Creating a
   Blackboard lane does not launch Pi Team.").

Issue #6's "保持 Blackboard 仅为观察面而非控制总线" requirement is therefore
**already met** at the architecture level. The protocol tightening
proposed in §4.1 only narrows the *cadence* and *content* of role-emitted
events; it does not change the control flow.
